## Recurrence prevention

The previous scheduler used `shutil.copy2` directly on the authoritative file.
That truncates the destination before the copy completes and does not capture
committed WAL contents. A failed copy can therefore destroy the last good backup.
This mechanism is consistent with the observed truncation; historical logs do
not establish the exact failing copy.

`persist_database` now uses SQLite's online backup API, stages on the destination
filesystem, checks free space with a reserve, validates the standalone snapshot,
and atomically replaces the persistent copy only after success. Failed writes,
invalid sources, and exhausted capacity leave the existing file untouched.

The isolated persistence safety workflow configures Python 3.11 and exercises
successful snapshots, committed WAL inclusion, initially full storage, storage
exhaustion mid-backup, replacement failure, corrupt input, missing paths, and
source/destination collision. Recovery commits marked `[skip deploy]` run these
tests without changing the production image. This patch is prevention, not a
repair of the already-truncated production database.

## Required recovery decision

Preserve the original before any recovery attempt. A verified complete production
backup, if one exists outside the inspected locations, is the preferred source.
Otherwise recovery must operate on a separate copy and may lose records whose
pages are missing. It must not silently replace the authoritative file.

Additional durable capacity or a topology/storage change needs explicit approval;
the shared B2 plan must not be scaled as an unattended outage workaround. Even
after approval, recover and integrity-check the database before a uniquely tagged
application deployment and live health/search verification.
